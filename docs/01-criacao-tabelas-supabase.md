# Criação das tabelas no Supabase — Parte 1

## 1. Objetivo

Esta etapa cria a estrutura inicial do banco do sistema de controle de faturamento:

- `empresas`;
- `usuarios`;
- `categorias_faturamento`;
- `competencias`;
- `historico_competencias`;
- `lancamentos_faturamento`.

Também serão configurados:

- tipos controlados;
- chaves primárias;
- relacionamentos;
- restrições básicas;
- índices;
- atualização automática de `updated_at`;
- Row Level Security — RLS;
- acesso exclusivo do backend.

Regras mais complexas, como transição de competências, imutabilidade dos lançamentos e cancelamento com substituição atômica, serão implementadas em migrations posteriores.

## 2. Conceitos importantes

### Migration

Uma migration é um arquivo SQL versionado que descreve uma alteração no banco.

Ela permite:

- recriar o banco;
- revisar mudanças pelo Git;
- manter diferentes ambientes sincronizados;
- saber quando cada alteração foi aplicada.

A pasta `supabase/migrations` deve ser versionada no Git. Consulte o [fluxo oficial de migrations do Supabase](https://supabase.com/docs/guides/local-development/cli-workflows).

### RLS

Row Level Security controla quais registros cada usuário pode acessar.

Nesta primeira migration, o RLS será habilitado, mas ainda não serão criadas policies para `anon` ou `authenticated`. Portanto, o frontend não poderá acessar diretamente as tabelas.

O backend utilizará uma chave secreta em ambiente protegido. Consulte a [documentação de RLS do Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 4. Adicionar o SQL

Abra o arquivo criado e adicione:

```sql
-- =========================================================
-- TIPOS CONTROLADOS
-- =========================================================

create type public.status_competencia as enum (
  'ABERTA',
  'EM_CONFERENCIA',
  'REABERTA',
  'FINALIZADA'
);

create type public.status_lancamento as enum (
  'ATIVO',
  'CANCELADO'
);

create type public.tipo_lancamento as enum (
  'FATURAMENTO',
  'DEVOLUCAO_ESTORNO'
);

-- =========================================================
-- EMPRESAS
-- =========================================================

create table public.empresas (
  id bigint generated by default as identity primary key,
  razao_social varchar(200) not null,
  nome_fantasia varchar(150),
  cnpj varchar(14) not null unique,
  ativa boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint empresas_cnpj_formato_check
    check (cnpj ~ '^[0-9]{14}$')
);

-- =========================================================
-- USUARIOS
-- =========================================================

create table public.usuarios (
  id uuid primary key
    references auth.users(id)
    on delete restrict,

  nome varchar(150) not null,
  email varchar(255) not null unique,
  cargo varchar(50) not null,
  ativo boolean not null default true,
  ultimo_login_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- =========================================================
-- CATEGORIAS DE FATURAMENTO
-- =========================================================

create table public.categorias_faturamento (
  id bigint generated by default as identity primary key,
  nome varchar(120) not null unique,
  descricao text,
  ativa boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- =========================================================
-- COMPETENCIAS
-- =========================================================

create table public.competencias (
  id bigint generated by default as identity primary key,

  empresa_id bigint not null
    references public.empresas(id)
    on delete restrict,

  ano integer not null,
  mes integer not null,

  status public.status_competencia not null default 'ABERTA',

  sem_movimento boolean not null default false,
  sem_movimento_em timestamptz,

  sem_movimento_por uuid
    references public.usuarios(id)
    on delete restrict,

  conferencia_iniciada_em timestamptz,

  conferencia_iniciada_por uuid
    references public.usuarios(id)
    on delete restrict,

  finalizada_em timestamptz,

  finalizada_por uuid
    references public.usuarios(id)
    on delete restrict,

  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint competencias_empresa_ano_mes_unique
    unique (empresa_id, ano, mes),

  constraint competencias_mes_check
    check (mes between 1 and 12),

  constraint competencias_sem_movimento_check
    check (
      (
        sem_movimento = false
        and sem_movimento_em is null
        and sem_movimento_por is null
      )
      or
      (
        sem_movimento = true
        and sem_movimento_em is not null
        and sem_movimento_por is not null
      )
    )
);

-- =========================================================
-- HISTORICO DAS COMPETENCIAS
-- =========================================================

create table public.historico_competencias (
  id bigint generated by default as identity primary key,

  competencia_id bigint not null
    references public.competencias(id)
    on delete restrict,

  usuario_id uuid not null
    references public.usuarios(id)
    on delete restrict,

  status_anterior public.status_competencia not null,
  status_novo public.status_competencia not null,
  justificativa text,
  created_at timestamptz not null default now(),

  constraint historico_status_diferentes_check
    check (status_anterior <> status_novo),

  constraint historico_reabertura_justificada_check
    check (
      status_anterior <> 'EM_CONFERENCIA'
      or status_novo <> 'REABERTA'
      or nullif(btrim(justificativa), '') is not null
    )
);

-- =========================================================
-- LANCAMENTOS DE FATURAMENTO
-- =========================================================

create table public.lancamentos_faturamento (
  id bigint generated by default as identity primary key,

  competencia_id bigint not null
    references public.competencias(id)
    on delete restrict,

  categoria_id bigint not null
    references public.categorias_faturamento(id)
    on delete restrict,

  criado_por_usuario_id uuid not null
    references public.usuarios(id)
    on delete restrict,

  tipo_lancamento public.tipo_lancamento not null,
  data_referencia date not null,
  valor numeric(14, 2) not null,
  observacao text,

  status public.status_lancamento not null default 'ATIVO',

  cancelado_por_usuario_id uuid
    references public.usuarios(id)
    on delete restrict,

  cancelado_em timestamptz,
  motivo_cancelamento text,

  substitui_lancamento_id bigint unique
    references public.lancamentos_faturamento(id)
    on delete restrict,

  created_at timestamptz not null default now(),

  constraint lancamentos_valor_positivo_check
    check (valor > 0),

  constraint lancamentos_nao_substitui_proprio_check
    check (
      substitui_lancamento_id is null
      or substitui_lancamento_id <> id
    ),

  constraint lancamentos_cancelamento_coerente_check
    check (
      (
        status = 'ATIVO'
        and cancelado_por_usuario_id is null
        and cancelado_em is null
        and motivo_cancelamento is null
      )
      or
      (
        status = 'CANCELADO'
        and cancelado_por_usuario_id is not null
        and cancelado_em is not null
        and nullif(btrim(motivo_cancelamento), '') is not null
      )
    )
);

-- =========================================================
-- INDICES
-- =========================================================

create index competencias_empresa_id_idx
  on public.competencias (empresa_id);

create index historico_competencias_competencia_id_idx
  on public.historico_competencias (competencia_id);

create index historico_competencias_usuario_id_idx
  on public.historico_competencias (usuario_id);

create index lancamentos_competencia_id_idx
  on public.lancamentos_faturamento (competencia_id);

create index lancamentos_categoria_id_idx
  on public.lancamentos_faturamento (categoria_id);

create index lancamentos_criado_por_idx
  on public.lancamentos_faturamento (criado_por_usuario_id);

create index lancamentos_data_referencia_idx
  on public.lancamentos_faturamento (data_referencia);

-- =========================================================
-- ATUALIZACAO AUTOMATICA DE updated_at
-- =========================================================

create or replace function public.atualizar_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

create trigger empresas_atualizar_updated_at
before update on public.empresas
for each row
execute function public.atualizar_updated_at();

create trigger usuarios_atualizar_updated_at
before update on public.usuarios
for each row
execute function public.atualizar_updated_at();

create trigger categorias_atualizar_updated_at
before update on public.categorias_faturamento
for each row
execute function public.atualizar_updated_at();

create trigger competencias_atualizar_updated_at
before update on public.competencias
for each row
execute function public.atualizar_updated_at();

-- =========================================================
-- ROW LEVEL SECURITY
-- =========================================================

alter table public.empresas enable row level security;
alter table public.usuarios enable row level security;
alter table public.categorias_faturamento enable row level security;
alter table public.competencias enable row level security;
alter table public.historico_competencias enable row level security;
alter table public.lancamentos_faturamento enable row level security;

-- O frontend não recebe acesso direto nesta primeira etapa.

revoke all on table public.empresas
  from anon, authenticated;

revoke all on table public.usuarios
  from anon, authenticated;

revoke all on table public.categorias_faturamento
  from anon, authenticated;

revoke all on table public.competencias
  from anon, authenticated;

revoke all on table public.historico_competencias
  from anon, authenticated;

revoke all on table public.lancamentos_faturamento
  from anon, authenticated;

-- A chave secreta utilizada pelo backend opera como service_role.

grant usage on schema public to service_role;

grant select, insert, update, delete
  on table
    public.empresas,
    public.usuarios,
    public.categorias_faturamento,
    public.competencias,
    public.historico_competencias,
    public.lancamentos_faturamento
  to service_role;

grant usage, select
  on all sequences in schema public
  to service_role;

revoke execute
  on function public.atualizar_updated_at()
  from public, anon, authenticated;
```

## 5. Configuração do RLS

Crie a segunda migration:

```powershell
npx supabase migration new corrigir_estrutura_inicial
```

Abra o arquivo criado e adicione:

```sql
-- A função é utilizada somente pelo event trigger que habilita RLS.
-- Nenhuma chamada pela Data API deve ser permitida.

revoke execute
on function public.rls_auto_enable()
from public, anon, authenticated, service_role;

-- Impede que novas funções sejam executáveis por padrão.
-- Permissões futuras deverão ser concedidas explicitamente.

alter default privileges
for role postgres
in schema public
revoke execute on functions from public;

alter default privileges
for role postgres
in schema public
revoke execute on functions from anon, authenticated;
```

## 6. O que essa migration já garante

### Empresas

- CNPJ obrigatório;
- CNPJ único;
- exatamente 14 números;
- empresa ativa por padrão;
- exclusão impedida quando houver relacionamento.

### Usuários

- o identificador é o mesmo do `auth.users`;
- e-mail único;
- usuário ativo por padrão;
- senha e sessão não são armazenadas na tabela pública.

### Categorias

- nome único;
- categoria ativa por padrão;
- categorias utilizadas não poderão ser excluídas.

### Competências

- uma única competência por empresa, ano e mês;
- mês entre 1 e 12;
- status inicial `ABERTA`;
- coerência dos campos de “sem movimento”.

### Histórico

- competência e usuário obrigatórios;
- status anterior diferente do novo;
- reabertura exige justificativa;
- exclusões relacionadas ficam bloqueadas.

### Lançamentos

- valor obrigatoriamente positivo;
- status inicial `ATIVO`;
- coerência dos campos de cancelamento;
- um lançamento não pode substituir a si próprio;
- somente um substituto direto por lançamento;
- nenhuma restrição impede vários lançamentos na mesma categoria e data.

## 7. O que ainda não está implementado

Esta migration não garante sozinha:

- que `data_referencia` pertence ao mês da competência;
- que uma empresa ou categoria está ativa;
- o fluxo fixo de status da competência;
- a criação automática do histórico;
- a imutabilidade dos lançamentos;
- o bloqueio de exclusão direta;
- que um lançamento substituto pertence à mesma competência;
- que cancelamento e substituição sejam atômicos;
- a criação automática do perfil em `public.usuarios`;
- policies de acesso para usuários autenticados.

Essas regras exigem funções, triggers, policies ou operações controladas pelo backend. Elas devem ser adicionadas separadamente para facilitar testes e revisão.

## 8. Validar antes de aplicar

Confira as migrations:

```powershell
npx supabase migration list
```

Visualize o que será enviado:

```powershell
npx supabase db push --dry-run
```

O `dry-run` não aplica alterações.

Se estiver utilizando Supabase local com Docker, valide recriando o banco local:

```powershell
npx supabase start
npx supabase db reset
```

O `db reset` local apaga e recria apenas o banco local. Não utilize `--linked`, pois isso apontaria para o projeto remoto.

## 9. Aplicar ao projeto remoto

Depois de revisar:

```powershell
npx supabase db push
```

Confira novamente:

```powershell
npx supabase migration list
```

As versões local e remota deverão aparecer alinhadas.

## 10. Conferir pelo Dashboard

No painel do Supabase:

1. Abra **Table Editor**.
2. Confirme a existência das seis tabelas.
3. Abra cada tabela e confira suas colunas.
4. Confirme que RLS está habilitado.
5. Abra **Database → Migrations** e confira a migration aplicada.
6. Abra **Database → Extensions** somente se uma migration futura exigir extensões adicionais.

Não crie ou altere colunas manualmente pelo Table Editor. As mudanças estruturais devem ser feitas por novas migrations.

## 11. Testar restrições

No SQL Editor do Supabase, teste um CNPJ inválido:

```sql
insert into public.empresas (
  razao_social,
  cnpj
)
values (
  'Empresa de teste',
  '123'
);
```

O banco deverá rejeitar a operação.

Teste um registro válido dentro de uma transação:

```sql
begin;

insert into public.empresas (
  razao_social,
  nome_fantasia,
  cnpj
)
values (
  'Empresa de aprendizado Ltda.',
  'Empresa de aprendizado',
  '12345678000199'
);

select *
from public.empresas
where cnpj = '12345678000199';

rollback;
```

O `rollback` desfaz o registro de teste.

## 12. Para Corrigir uma migration

Se ela ainda não foi enviada ao projeto remoto, edite o mesmo arquivo e teste novamente.

Se ela já foi aplicada, não altere o arquivo antigo. Crie outra migration:

```powershell
npx supabase migration new corrigir_estrutura_inicial
```

Isso preserva um histórico confiável das alterações do banco.
